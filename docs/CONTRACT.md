# חוזה דיגיטלי — Runbook

דף `/contract/` מאפשר לזוג לקרוא את החוזה, למלא את פרטיו ולחתום דיגיטלית.
יריב מקבל מייל עם PDF חתום; הזוג מקבל עותק; העותק נשמר בארכיון.

---

## השימוש היומיומי: יצירת קישור לזוג

**הדרך הרגילה היא דף `/admin`** — נכנסים עם סיסמה, ממלאים טופס, מקבלים קישור
והודעת וואטסאפ. לא צריך טרמינל, לא צריך `.env`, עובד גם מהטלפון.
הפירוט ב-[docs/ADMIN.md](ADMIN.md).

מה שלמטה הוא ה-fallback מהטרמינל: כשאין רשת, כשהסיסמה אבדה, או כשרוצים לייצר
קישור בתוך סקריפט (`--json`). שני המסלולים משתמשים באותה ולידציה ובאותו סוד,
ולכן מייצרים בדיוק את אותו קישור.

```bash
npm run contract:link -- \
  --couple "דנה לוי ואורי כהן" \
  --date 2027-06-18 \
  --venue "אחוזת טל, קיסריה" \
  --guests 300 \
  --total 15000 --deposit 3000 \
  --services all \
  --signers 2 \
  --pay bit --balance-due event-day \
  --email dana@example.com --phone 0501234567 \
  --days 30
```

בלי דגלים — הסקריפט ישאל הכול בשאלות.

הפלט מדפיס **סיכום של התנאים כפי שהזוג יראה אותם** — הגיהו אותו לפני
השליחה — ואז את הקישור (שגם מועתק ללוח) והודעת וואטסאפ מוכנה.

### הדגלים

| דגל | ערכים | ברירת מחדל |
|---|---|---|
| `--services` | `all` · רשימה (`stills1,video1`) · חיסור (`all,-std`) | `all` |
| `--signers` | `1` · `2` | `1` |
| `--pay` | `bank` · `bit` · `cash` | `bit` |
| `--balance-due` | `event-day` · `5-days` | `event-day` |
| `--days` | תוקף בימים, מקסימום 90 | `30` |
| `--local` | מפנה ל-`localhost:8888` לבדיקות | — |
| `--json` | פלט מכונה | — |

מזהי השירותים: `stills1 stills2 video1 video2 film photos gallery albums std`
— מוגדרים ב-`src/data/contract.js`, שם ורק שם.

**שני דברים שנגזרים אוטומטית ולא צריך להעביר:**
- היתרה = תמורה פחות מקדמה.
- סעיף 8.2 (מחיר האלבומים) — אם `albums` ברשימת השירותים, הסעיף יגיד
  "כלול בחבילה"; אחרת יופיע המחיר 1,500 ₪.

**התפוגה נצמדת לתאריך האירוע.** קישור לתאריך שכבר עבר לא ייווצר בכלל.

## הארכיון

```bash
npm run contract:list              # כל החוזים החתומים
npm run contract:get -- <מזהה>     # הורדת PDF בודד
```

דורש שהאתר יהיה מקושר: `npx netlify link`.

## הגדרה חד-פעמית

### 1. הסוד

```bash
node -e "console.log(crypto.randomBytes(32).toString('hex'))"
```

לשים ב-`site/.env` בתור `CONTRACT_LINK_SECRET`, ואת אותו ערך ב-Netlify:

```bash
netlify env:set CONTRACT_LINK_SECRET <הערך> --secret --scope functions
```

ה-scope חשוב: כך הסוד לא נחשף ל-build ולא ללקוח.

### 2. החתימה של יריב

```bash
node scripts/contract-signature.mjs ~/Desktop/signature.png
```

צילום או סריקה של החתימה על **נייר לבן**. הסקריפט חותך לדיו, מסיר את הרקע
ושומר PNG שקוף ב-`netlify/functions/lib/signature-yariv.mjs`.

**זה לא נכנס ל-`public/`** — קובץ שם היה עותק של חתימה אמיתית שכל אחד יכול
להוריד. בתוך חבילת הפונקציה הוא לעולם לא מגיע לדפדפן: הדף משאיר תיבה ריקה
והשרת חותם.

עד שהקובץ קיים, במקום החתימה מודפס "נחתם דיגיטלית על ידי Brothers
Photography" עם מזהה המסמך. החוזה תקף — הוא פשוט נראה פחות טוב.

### 3. מיילים (Resend)

1. חשבון ב-resend.com, ליצור API key → `RESEND_API_KEY`.
2. **עד לאימות הדומיין**, Resend שולח רק מ-`onboarding@resend.dev` ורק
   לכתובת של בעל החשבון. לכן `CONTRACT_MAIL_MODE=test`: שני העותקים הולכים
   ליריב, והעותק "של הזוג" מקבל באנר שאומר לאן הוא היה אמור להישלח.
   הכישלון הזה גלוי במקום שקט.
3. לאימות: Resend → Domains → להוסיף **`send.brothers-photography.com`**
   (תת-דומיין, לא הדומיין הראשי — כך רשומות ה-SPF וההגדרות של הג'ימייל
   הקיים לא נוגעים). להוסיף את שלוש הרשומות ב-Netlify DNS.
4. אחרי שהדומיין ירוק:
   - `CONTRACT_MAIL_FROM=Brothers Photography <contracts@send.brothers-photography.com>`
   - `CONTRACT_MAIL_MODE=live`

## פיתוח מקומי

```bash
npx netlify dev            # → http://localhost:8888
npm run contract:test      # בדיקות האבטחה
```

**חייבים פורט 8888, לא 4321.** `netlify dev` מריץ את Astro מאחוריו ומגיש גם
את `/.netlify/functions/*`. ב-4321 הפונקציות פשוט לא קיימות.

> `src/scripts/leadForm.js` עוקף שליחה ב-localhost כי Netlify **Forms** באמת
> לא עובדים ב-dev. Netlify **Functions** כן. אין ב-`contractPage.js` עקיפה
> כזו בכוונה — היא הייתה הופכת את הפיצ'ר לבלתי-ניתן-לבדיקה מקומית.

## רוטציית סוד

מחליפים סוד? הקישורים שכבר נשלחו מתבטלים. כדי לא לנטוש זוג באמצע חתימה:

1. `CONTRACT_LINK_SECRET_PREV` = הסוד הישן
2. `CONTRACT_LINK_SECRET` = החדש
3. אחרי שכל הקישורים הישנים פגו (מקסימום 90 יום) — למחוק את `_PREV`

## איך זה בנוי

```
קישור חתום (HMAC)  →  contract-verify  →  הדף מרנדר מהתשובה בלבד
                                            ↓
                                        הזוג ממלא + חותם
                                            ↓
                        הדפדפן מרסטר עמודי A4  (html2canvas-pro)
                                            ↓
                   contract-sign → pdf-lib מרכיב + חותם + ראיות
                                            ↓
                      Blobs (ארכיון)  →  Resend (יריב + הזוג)
```

**למה הדפדפן מייצר את ה-PDF ולא השרת:** ל-pdf-lib אין BIDI. החוזה מלא
ברצפים מעורבים (`₪ 15,000`, `18:30`, `DSLR`, `Save the Date`, `30×80 ס"מ`)
והיפוך ידני שלהם הוא מקור מספר אחת לחוזה שנקרא הפוך. הדפדפן כבר פתר את זה
— אנחנו מצלמים את התוצאה, והשרת מהדק אותה ל-PDF.

**למה יש אחסון בכלל:** בלי רשומה אין תשובה לשאלה "האם החוזה הזה כבר נחתם",
וכישלון זמני של Resend היה מוחק חתימה של זוג. הסדר הוא: לארכב, ורק אז
לשלוח — כך ניסיון חוזר שולח מחדש ולא חותם מחדש.

**למה הטוקן ב-fragment ולא ב-query:** באתר רצים GA4 ו-Meta Pixel.
`?c=<token>` היה נוחת ב-`page_location` של אנליטיקס, בלוגים ובכותרות
`Referer` — כלומר אמצעי הגישה למסמך שמכיל שתי תעודות זהות. ב-fragment הוא
לא נשלח לאף שרת. בדף `/contract/` עצמו, אגב, לא רץ שום סקריפט צד-שלישי.

### פרטיות

הרשומות מכילות שתי תעודות זהות. **אסור ללוגג את גוף הבקשה או את הרשומה**
בפונקציות — הלוגים של Netlify נשמרים וגלויים בלוח הבקרה.

### שינוי נוסח החוזה

הכול ב-`src/data/contract.js`. **חובה להעלות את `contractVersion`** בכל
שינוי בנוסח המשפטי: הגרסה נרשמת בכל PDF חתום, וכך אפשר תמיד להתאים חוזה
בארכיון לנוסח שהיה על המסך באותו רגע.
